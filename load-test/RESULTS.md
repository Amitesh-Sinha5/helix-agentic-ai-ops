### Cache vs. agent path

The semantic cache is the single biggest lever on both latency and cost:

| Path | Avg | p95 | Requests |
|---|---|---|---|
| Cache hit | **5.5 ms** | **10.7 ms** | 4,848 |
| Full agent graph | **26.6 ms** | **38.5 ms** | 256 |

A cached answer is served roughly **3.6× faster at p95** and, more importantly,
for **zero LLM cost** — the avoided call is recorded in telemetry and surfaces as
`estimated_cost_saved_usd` on `/observability/summary`.

| Metric | Value |
|---|---|
| Answered (grounded) rate | 95.2% |

The abstentions are the intended behaviour, not errors: 5% of generated traffic
asks deliberately out-of-scope questions, and every one of them returned
"I could not find that in the provided documents" rather than a confabulation.
That assertion is part of the load test itself, so a regression that made the
pipeline answer everything would fail the run, not just slow it down.

## Reading these numbers honestly

**These figures measure Helix's orchestration overhead, not end-to-end product
latency.** The run uses the `mock` LLM provider, so there is no model inference
and no network round trip. What the numbers legitimately show is that the
framework around the model — routing, auth, rate limiting, hybrid retrieval,
RRF, reranking, the LangGraph state machine, guardrail validation, telemetry
and persistence — costs about **27 ms of wall clock per uncached request** and
holds 50 req/s on one worker with zero failures.

With a real provider, per-request latency is dominated by the model: the Doc Q&A
graph makes 5–7 LLM calls on the uncached path, so expect **seconds**, not
milliseconds. Two things from this run still carry over directly:

- the **cache hit path** genuinely avoids all of that work, so its ~5 ms stays ~5 ms;
- the **fixed overhead** stays ~27 ms, i.e. a small fraction of real latency.

The **94.9% cache hit rate is optimistic** and should not be read as a
production figure. The generated traffic draws from only 12 distinct questions,
so nearly everything repeats. Real traffic has a much longer tail. The useful
comparison is the *per-path* latency above, not the aggregate.

## Reproducing

```bash
# 1. Start a backend (mock provider, SQLite, no Redis needed)
cd backend
DATABASE_URL="sqlite+aiosqlite:///./loadtest.db" .venv/bin/alembic upgrade head
LLM_PROVIDER=mock RATE_LIMIT_ENABLED=false \
  DATABASE_URL="sqlite+aiosqlite:///./loadtest.db" \
  .venv/bin/python -m uvicorn app.main:app --port 8010

# 2. Run the load test
BASE_URL=http://127.0.0.1:8010 k6 run load-test/k6-script.js
```

`RATE_LIMIT_ENABLED=false` is required: the Free tier allows 20 requests/day, so
the limiter would (correctly) reject the load generator after 20 requests.
